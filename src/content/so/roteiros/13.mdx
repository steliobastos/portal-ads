<Passo numero={1} de={7} titulo="O primeiro script que roda">

<Intro>Um script é um arquivo de texto com comandos. Três coisas o tornam executável: o shebang, o conteúdo e a permissão.</Intro>

<Comando passo={1} cmd="nano ~/monitor.sh">

  <Explica>
    <Caixa titulo="O que é">

    A primeira linha, `#!/bin/bash`, é o **shebang**: diz ao sistema qual programa deve interpretar este arquivo. Sem ela, o SO não sabe que é um script bash.

    </Caixa>
    <Caixa titulo="Por que importa">

    É o que transforma um arquivo de texto qualquer num programa executável. Nenhuma compilação é necessária — o shell já é o interpretador.

    </Caixa>
  </Explica>

  <Terminal>{`#!/bin/bash

echo "Monitor de sistema"
echo "Executado por: $USER"`}</Terminal>

  <Esperar>
    salve com `Ctrl+O`, Enter, `Ctrl+X`. Depois rode `chmod +x ~/monitor.sh` e execute com `~/monitor.sh`. O `$USER` é uma variável que o próprio sistema já define com seu nome de usuário.
  </Esperar>

  <Dica titulo='Deu "Permission denied"'>

  Faltou o `chmod +x ~/monitor.sh`. Esse é o erro mais comum de quem começa: o arquivo existe e o conteúdo está certo, mas sem a permissão de execução o sistema se recusa a rodá-lo. Confira com `ls -l ~/monitor.sh` — devem aparecer `x` nas permissões.

  </Dica>

</Comando>

</Passo>

<Passo numero={2} de={7} titulo="Variáveis e a captura da saída de um comando">

<Intro>Este é o conceito mais importante do encontro: um script pode guardar o **resultado** de um comando numa variável e decidir o que fazer com ele.</Intro>

<Comando passo={2} cmd="Acrescente ao monitor.sh">

  <Explica>
    <Caixa titulo="O que é">

    `VAR="valor"` atribui — **sem espaços em volta do `=`**. `$(comando)` executa o comando e devolve a saída dele, que pode ser guardada numa variável.

    </Caixa>
    <Caixa titulo="Por que importa">

    É o que permite o script *reagir ao estado real da máquina*, em vez de executar sempre a mesma coisa cegamente.

    </Caixa>
  </Explica>

  <Terminal>{`#!/bin/bash

LIMITE=80
DATA=$(date +%F)
USO=$(df / | tail -1 | awk '{print $5}' | tr -d '%')

echo "Data: $DATA"
echo "Uso do disco: \${USO}%"
echo "Limite configurado: \${LIMITE}%"`}</Terminal>

  <Esperar>
    o script imprime a data de hoje e o percentual real de uso do seu disco. A linha do `USO` é um pipeline do Encontro 6: pega a saída do `df`, fica com a última linha, extrai a 5ª coluna e remove o símbolo `%` — sobrando só o número.
  </Esperar>

  <Dica titulo="Por que as chaves em ${USO}%?">

  As chaves delimitam onde o nome da variável termina. Sem elas, `$USO%` ainda funcionaria neste caso, mas `$USOpercent` faria o shell procurar uma variável chamada `USOpercent`, que não existe. Usar `${}` sempre que houver texto colado é um bom hábito.

  </Dica>

  <Dica titulo='Erro: "LIMITE: command not found"'>

  Você deixou espaço em volta do `=`. Em bash, `LIMITE = 80` é interpretado como "execute o comando `LIMITE` com os argumentos `=` e `80`". Escreva sempre `LIMITE=80`, sem espaço algum.

  </Dica>

</Comando>

<Rascunho encontro={13} numero={1} exemplo="Ex: o $(...) executa o comando e guarda a saída na variável, o que permite...">
  o que a construção $(...) faz, e por que ela é essencial para um script de monitoramento? Use a linha do USO como exemplo.
</Rascunho>

<Passo numero={3} de={7} titulo="Fazendo o script decidir">

<Intro>Com o valor capturado, o script pode comparar e agir de formas diferentes conforme o resultado.</Intro>

<Comando passo={3} cmd="Acrescente a condicional">

  <Explica>
    <Caixa titulo="O que é">

    `if [ condição ]; then ... else ... fi`. Os **espaços dentro dos colchetes são obrigatórios**, e `-gt` significa "maior que" para números.

    </Caixa>
    <Caixa titulo="Por que importa">

    Sem condicional, um monitor não monitora — ele apenas imprime. É o `if` que transforma dado em decisão.

    </Caixa>
  </Explica>

  <Terminal>{`if [ "$USO" -gt "$LIMITE" ]; then
  echo "ALERTA: disco em \${USO}%, acima do limite de \${LIMITE}%"
else
  echo "OK: disco em \${USO}%, dentro do limite"
fi`}</Terminal>

  <Esperar>
    provavelmente a mensagem "OK". Para testar o outro caminho, baixe temporariamente o limite (`LIMITE=10`) e rode de novo — o script deve passar a alertar. Depois volte para 80.
  </Esperar>

  <Dica titulo='Por que as aspas em "$USO" e "$LIMITE"?'>

  Sem aspas, uma variável **vazia desaparece** da linha, e uma com **espaços vira várias palavras**. O caso mais traiçoeiro é o teste de texto: com `NOME` vazio, `[ -n $NOME ]` vira `[ -n ]`, que dá **verdadeiro** — o script conclui que há um nome quando não há. Com aspas, `[ -n "$NOME" ]` vira `[ -n "" ]`, que dá falso, como deveria. **Sempre use aspas em volta de variáveis** — é a regra que evita mais bugs em shell script.

  Atenção a um limite da regra: no teste **numérico**, aspas não bastam. Se `USO` vier vazio, tanto `[ $USO -gt 80 ]` quanto `[ "$USO" -gt "80" ]` imprimem um erro, a condição fica falsa e o script cai no `else` — dizendo "OK" sem ter medido nada. Por isso um monitor sério confere antes se o valor é mesmo um número (é o desafio do fim do roteiro).

  </Dica>

  <Dica titulo='Erro: "[: missing ]" ou similar'>

  Faltou espaço dentro dos colchetes. `[$USO -gt $LIMITE]` está errado; o certo é `[ "$USO" -gt "$LIMITE" ]`, com espaço depois do `[` e antes do `]`. O `[` é, na verdade, um comando — e comandos precisam ser separados dos argumentos por espaço.

  </Dica>

</Comando>

</Passo>

<Passo numero={4} de={7} titulo="Repetindo para vários itens">

<Intro>O laço `for` aplica uma sequência inteira de comandos a cada item de uma lista — indo além do que o coringa do Encontro 12 permitia.</Intro>

<Comando passo={4} cmd="Acrescente o laço">

  <Explica>
    <Caixa titulo="O que é">

    `for VAR in lista; do ... done`. A cada volta, `VAR` assume o valor do item seguinte da lista.

    </Caixa>
    <Caixa titulo="Por que importa">

    O coringa aplica *um* comando a muitos arquivos. O `for` aplica uma *sequência de decisões* a cada um — inclusive com `if` dentro.

    </Caixa>
  </Explica>

  <Terminal>{`echo "--- Verificando pontos de montagem ---"
for PONTO in / /home /tmp; do
  if [ -d "$PONTO" ]; then
    ESPACO=$(df -h "$PONTO" | tail -1 | awk '{print $4}')
    echo "$PONTO tem $ESPACO livres"
  else
    echo "$PONTO não existe nesta máquina"
  fi
done`}</Terminal>

  <Esperar>
    uma linha por caminho. O teste `-d` verifica se o diretório existe antes de consultar o `df` — assim o script não quebra se receber um caminho que não existe nesta máquina. Esse tipo de defesa é o que diferencia script frágil de script confiável. Repare também: se `/home` não for uma partição separada (o caso da sua VM), o `df` mostra o sistema de arquivos que o contém — o mesmo de `/` — e os dois aparecem com o mesmo espaço livre.
  </Esperar>

</Comando>

</Passo>

<Passo numero={5} de={7} titulo="Uma função para registrar log">

<Intro>Quando o mesmo trecho se repete em vários pontos, ele vira função — e passa a ter um só lugar para ser corrigido.</Intro>

<Comando passo={5} cmd="Adicione a função log() no topo (logo após o shebang)">

  <Explica>
    <Caixa titulo="O que é">

    `nome() { ... }` define a função. Dentro dela, `$1` é o primeiro argumento recebido na chamada.

    </Caixa>
    <Caixa titulo="Por que importa">

    Se amanhã o formato do log mudar, você altera um lugar só — em vez de caçar todos os `echo` espalhados pelo script.

    </Caixa>
  </Explica>

  <Terminal>{`#!/bin/bash

ARQUIVO_LOG=~/monitor.log

log() {
  echo "[$(date +'%F %T')] $1" | tee -a "$ARQUIVO_LOG"
}

# ... resto do script ...
log "Verificação iniciada"`}</Terminal>

  <Esperar>
    a mensagem aparece na tela **e** é gravada no arquivo. O `tee -a` faz as duas coisas ao mesmo tempo (o `-a` é de "append", equivalente ao `>>` do Encontro 12). Confira com `cat ~/monitor.log`.
  </Esperar>

  <Dica titulo="Por que a função precisa vir antes de ser chamada?">

  O bash lê o script de cima para baixo. Se você chamar `log` numa linha anterior à definição da função, ele ainda não sabe que ela existe e dá "command not found". Por isso funções ficam sempre no topo, logo após o shebang.

  </Dica>

</Comando>

<Rascunho encontro={13} numero={2} exemplo="Ex: se o formato mudar, preciso alterar só um lugar, e além disso...">
  qual a vantagem de usar uma função log() em vez de repetir echo em vários pontos do script?
</Rascunho>

<Passo numero={6} de={7} titulo="O script completo">

<Intro>Junte tudo. Este é o resultado final — um monitor de disco funcional, com log e código de saída.</Intro>

<Comando passo={6} cmd="Versão final do monitor.sh">

  <Explica>
    <Caixa titulo="O que é">

    Todas as peças anteriores integradas, mais o `exit` com código apropriado ao final.

    </Caixa>
    <Caixa titulo="Por que importa">

    O `exit 1` sinaliza erro a quem chamou o script — é assim que uma ferramenta de agendamento ou um pipeline sabe que algo deu errado.

    </Caixa>
  </Explica>

  <Terminal>{`#!/bin/bash

ARQUIVO_LOG=~/monitor.log
LIMITE=80

log() {
  echo "[$(date +'%F %T')] $1" | tee -a "$ARQUIVO_LOG"
}

log "Verificação iniciada"

USO=$(df / | tail -1 | awk '{print $5}' | tr -d '%')

if [ "$USO" -gt "$LIMITE" ]; then
  log "ALERTA: disco em \${USO}%, acima do limite"
  exit 1
else
  log "OK: disco em \${USO}%"
  exit 0
fi`}</Terminal>

  <Esperar>
    depois de rodar, verifique o código de saída com `echo $?` — deve ser `0` se estiver OK. Teste também `~/monitor.sh && echo "tudo certo"`: a segunda parte só executa se o script sair com 0, exatamente como o `&&` que vocês usam desde o Encontro 5.
  </Esperar>

  <Esperar>
    **Desafio:** faça o script sair com código `2` e uma mensagem de erro se `USO` não for um número (dica: `[[ "$USO" =~ ^[0-9]+$ ]]` testa se a variável só tem dígitos).
  </Esperar>

</Comando>

</Passo>

<Passo numero={7} de={7} titulo="Um script que garante o container no ar">

<Intro>Última peça: um script que verifica se o container está rodando e, se não estiver, o sobe. É o embrião do toolkit do projeto final.</Intro>

<Comando passo={7} cmd="nano ~/garante_container.sh">

  <Explica>
    <Caixa titulo="O que é">

    `docker ps -q -f name=...` devolve o ID do container se ele estiver rodando, ou **nada** se não estiver. O teste `-z` verifica se a variável ficou vazia.

    </Caixa>
    <Caixa titulo="Por que importa">

    É a lógica básica de qualquer ferramenta de orquestração: verificar o estado desejado e agir só quando ele não for o real.

    </Caixa>
  </Explica>

  <Terminal>{`#!/bin/bash

NOME=meuservico
RODANDO=$(docker ps -q -f name="$NOME")

if [ -z "$RODANDO" ]; then
  echo "Container $NOME não está no ar. Subindo..."
  docker run -d --name "$NOME" alpine sleep 600
else
  echo "Container $NOME já está rodando (ID: $RODANDO)"
fi`}</Terminal>

  <Esperar>
    na primeira execução, o script sobe o container. **Rode uma segunda vez** — agora ele deve detectar que já está no ar e não fazer nada. Essa propriedade (rodar várias vezes sem causar estrago) é justamente o que se espera de um script de automação.
  </Esperar>

  <Dica titulo="Segunda execução deu erro de nome já em uso">

  Significa que o container existe mas está **parado** — o `docker ps -q` só lista os que estão rodando. Remova com `docker rm $NOME` e rode de novo. Um script de produção trataria esse caso também, verificando com `docker ps -aq`; fica como desafio.

  </Dica>

  <Esperar>
    **Limpeza:** `docker stop meuservico && docker rm meuservico`.
  </Esperar>

</Comando>

  </Exemplo>
  <Exemplo tipo="forte">

  "O `$(...)` executa o comando e substitui a expressão pela saída dele. Na linha `USO=$(df / | tail -1 | awk '{print $5}' | tr -d '%')`, todo o pipeline roda primeiro e só o número final (ex.: 36) é guardado em `USO`. Sem isso, o script só conseguiria imprimir a saída do `df` na tela; com isso, ele consegue **comparar** esse valor com o limite e decidir se alerta. É o que separa um script que informa de um que monitora."
