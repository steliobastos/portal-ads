PASSO 1 DE 6

Provocando um processo CPU-bound

Vamos criar, de propósito, um processo que só calcula sem parar — sem nunca esperar por disco ou rede.

1 yes > /dev/null & depois top
O que é

yes imprime "y" infinitamente. O > /dev/null descarta a saída (senão lotaria a tela), e o & manda rodar em segundo plano.

Por que importa

É o exemplo mais simples de processo CPU-bound: nunca bloqueia esperando E/S, só usa CPU sem parar.

$ yes > /dev/null & [1] 5231 $ top %Cpu(s): 99.7 us PID USER %CPU %MEM COMMAND 5231 aluno 99.3 0.0 yes

O que esperar: no top, o processo yes deve aparecer perto de 100% de CPU (de um núcleo), sozinho no topo da lista. Aperte q pra sair do top — o yes continua rodando em segundo plano.

Como eu paro o yes depois?
Rode kill %1 (usa o número de "job" que apareceu entre colchetes) ou descubra o PID com ps aux | grep yes e rode kill <PID>. Não esqueça — ele fica consumindo CPU até você matá-lo ou fechar o terminal.
PASSO 2 DE 6

Provocando um processo I/O-bound

Agora um processo que mexe bastante com disco, mas usa pouca CPU — a espera é do disco, não do processador.

2 dd if=/dev/zero of=arquivo_grande bs=1M count=1000; sync
O que é

dd copia 1000 blocos de 1 MB cheios de zeros pra um arquivo novo — cria ~1 GB de dado gravado em disco. sync garante que tudo foi realmente escrito.

Por que importa

Processo claramente I/O-bound: o gargalo é a velocidade do disco, não da CPU — por isso o consumo de CPU fica baixo mesmo "trabalhando".

$ dd if=/dev/zero of=arquivo_grande bs=1M count=1000; sync 1000+0 registros de entrada 1000+0 registros de saída 1048576000 bytes (1,0 GB) copiados

O que esperar: se você rodar top em outro terminal enquanto o dd executa, o processo aparece consumindo bem menos CPU que o yes do passo 1 — mesmo movendo 1 GB de dado.

Não deu tempo de ver o dd rodando no top
Normal em discos rápidos (SSD) — o dd pode terminar rápido demais. Aumente count=1000 pra count=3000 e tente de novo, observando o top em paralelo.

PASSO 3 DE 6

Separando saída normal de erro

Vamos provocar um erro de propósito e confirmar que stdout e stderr são, de fato, dois canais separados.

3 ls arquivo_inexistente 2> erro.txt; cat erro.txt
O que é

2> redireciona só o canal 2 (stderr) pro arquivo erro.txt. A mensagem de erro do ls vai pro arquivo, não pra tela.

Por que importa

Prova, na prática, que stdout (1) e stderr (2) são canais independentes — por isso dá pra guardar só os erros de um comando sem perder a saída normal.

$ ls arquivo_inexistente 2> erro.txt; cat erro.txt ls: não é possível acessar 'arquivo_inexistente': Arquivo ou diretório inexistente

O que esperar: nada aparece na tela quando você roda o ls (o erro foi direto pro arquivo) — só o cat erro.txt seguinte mostra a mensagem.

PASSO 4 DE 6

Encadeando processos com pipes

Vamos contar quantos processos existem, e depois filtrar antes de contar — dois pipelines curtos.

4 ps aux | wc -l e ps aux | grep bash | wc -l
O que é

wc -l conta linhas. O primeiro pipe conta todos os processos; o segundo filtra só os que têm "bash" antes de contar.

Por que importa

Mostra um pipeline de três processos encadeados de uma vez — exatamente o que o slide de hoje explicou por dentro.

$ ps aux | wc -l 87 $ ps aux | grep bash | wc -l 2

O que esperar: o primeiro número deve ser bem maior que o segundo. O "2" do segundo comando inclui o seu terminal bash e o próprio processo grep bash que acabou de rodar (o mesmo efeito visto no Encontro 5).

PASSO 5 DE 6

Vendo o consumo de um container ao vivo

Depois de tanto observar processos comuns, vamos ver o mesmo tipo de informação, só que organizada por container.

5 docker run -d --name statsdemo alpine sleep 300 depois docker stats --no-stream
O que é

Sobe um container ocioso (só sleep), e docker stats --no-stream tira uma "fotografia" única do consumo de todos os containers rodando.

Por que importa

É o top/ps do mundo Docker — mas organizado por container, não por processo do sistema inteiro.

$ docker run -d --name statsdemo alpine sleep 300 a13f0e9c7d21... $ docker stats --no-stream NAME CPU % MEM USAGE / LIMIT NET I/O statsdemo 0.00% 1.2MiB / 3.8GiB 906B / 0B

O que esperar: o statsdemo deve aparecer com CPU próxima de 0% — ele só está dormindo (sleep), sem nenhum trabalho de verdade pra fazer.

Quero comparar com um container "ocupado"
Se sobrar tempo, tente docker run -d --name cpudemo alpine sh -c "yes > /dev/null" e rode docker stats --no-stream de novo — agora deve aparecer um container consumindo bem mais CPU, do mesmo jeito que o yes do passo 1.

PASSO 6 DE 6

Encerrando e limpando

Antes de fechar, pare e remova o container criado neste roteiro (e o processo yes do passo 1, se ainda estiver rodando).

6 docker stop statsdemo && docker rm statsdemo
O que é

docker stop encerra o container, docker rm remove o registro dele. Confira também se o yes do passo 1 já foi encerrado.

Por que importa

Boa prática básica: não deixar processos ou containers de teste "esquecidos" consumindo recursos depois da aula.

O que esperar: o nome statsdemo impresso duas vezes, confirmando parada e remoção. Rode ps aux | grep yes pra garantir que nenhum yes ficou pra trás.

Exemplo de observação forte x fraca

Observação fraca

"O yes usou mais CPU que o dd."

Observação forte

"O yes ficou perto de 100% de CPU porque é puramente CPU-bound — só calcula e imprime, sem nunca parar pra esperar nada. Já o dd, mesmo movendo 1 GB pro disco, ficou com CPU baixa, porque o gargalo real era a velocidade de escrita do disco, não o processamento."
