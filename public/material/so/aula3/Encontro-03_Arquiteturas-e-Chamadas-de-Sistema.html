Grupo 1 · seu card

Núcleo monolítico

Tudo — processos, memória, arquivos, drivers — roda dentro de um único bloco de código, no mesmo espaço de endereçamento e com privilégios máximos.

Aplicação
Aplicação
Núcleo (processos + memória + arquivos + drivers, tudo junto)
Hardware
A favor

Rápido: um módulo chama o outro direto, sem burocracia de mensagens entre processos separados.

Contra

Frágil: um driver de dispositivo com defeito roda com privilégio total e pode derrubar o sistema inteiro.

Exemplos: Linux e Windows são, na essência, monolíticos — mesmo sendo os SOs mais usados do planeta.

Grupo 2 · seu card

Sistema em camadas

O mesmo trabalho do monolítico, mas organizado em níveis empilhados: cada camada só enxerga e usa a camada logo abaixo dela.

Camada 4 — programas do usuário
Camada 3 — E/S de dispositivos
Camada 2 — comunicação entre processos
Camada 1 — memória e escalonamento
Camada 0 — hardware
A favor

Mais fácil de entender e depurar: cada camada tem uma responsabilidade clara e uma "fronteira" definida.

Contra

Definir onde cada função entra é difícil, e forçar tudo a passar camada por camada custa desempenho.

Pioneiro: o sistema THE de Dijkstra (1968) — a ideia inspirou como pensamos em SOs até hoje, mesmo quando o código real não é tão limpo assim.

Grupo 3 · seu card

Micronúcleo

Só o essencial fica dentro do núcleo (com privilégio total). Tudo o resto — driver de disco, sistema de arquivos, driver de rede — vira processo comum, rodando no espaço do usuário.

App
Driver de disco
Sist. de arquivos
micronúcleo
Hardware
A favor

Muito mais confiável: se o driver de áudio travar, ele derruba só o áudio — não o sistema inteiro.

Contra

Mais lento (processos precisam trocar mensagens entre si) e mais difícil de manter no dia a dia.

Onde importa de verdade: sistemas de missão crítica — controle industrial, aviônica, o QNX que roda em caças e usinas.

Máquina virtual

Em vez de dividir o núcleo, um programa especial (o monitor/hipervisor) finge, pra cada sistema operacional "convidado", que ele tem um hardware inteiro só pra si.

Isolamento forte entre sistemas — cada VM tem seu próprio núcleo completo, sem enxergar as outras.

Eixo do curso

Onde entra o Docker nessa história?

Pegadinha: um container não é uma 5ª arquitetura. Ele não tem núcleo próprio — todos os containers de uma máquina compartilham o mesmo núcleo Linux (normalmente monolítico) por baixo.

Máquina virtual

Núcleo completo por convidado

VirtualBox roda um Linux inteiro (kernel, drivers, tudo) dentro de outro Linux. Pesado, mas isolado por completo.

Container

Um núcleo, processos isolados

Docker usa namespaces e cgroups do próprio núcleo Linux pra fazer um processo achar que está sozinho na máquina — sem carregar um SO novo.

É por isso que um container sobe em milissegundos e uma VM leva segundos ou minutos: o container não faz boot de núcleo nenhum — o núcleo já está rodando, ele só empresta um pedaço isolado dele.

Segunda metade do encontro

Como um programa pede ajuda ao SO

Não importa a arquitetura escolhida: todo SO precisa de um jeito controlado de deixar um programa comum acessar recursos protegidos (disco, rede, outros processos). Esse jeito se chama chamada de sistema (system call).

Modo usuário
  • Onde seu programa roda normalmente
  • Acesso restrito — não pode mexer direto no disco ou na rede
  • Se travar, não derruba o sistema
syscall
→
trap
Modo privilegiado (núcleo)
  • Acesso irrestrito a todo o hardware
  • Só o núcleo do SO roda aqui
  • Executa a chamada e devolve o controle

Pense na chamada de sistema como uma campainha: seu programa toca a campainha (a syscall), o núcleo atende, faz o trabalho perigoso por você, e devolve a resposta.

Do abstrato pro concreto

Chamadas de sistema que você já usa sem saber

Toda vez que um programa abre um arquivo, lê teclado ou cria outro processo, ele está, por baixo dos panos, chamando uma dessas.

O conjunto de chamadas que um núcleo oferece define sua API. No Linux/Unix, esse padrão se chama POSIX. No Windows, é o Win32.

Prévia da prática

Dá pra ver uma chamada de sistema acontecendo

Existe um comando que "escuta" toda vez que um programa toca a campainha do núcleo, e imprime cada chamada na tela: strace.

Cada linha acima é uma chamada de sistema de verdade, na ordem em que o programa ls as executou. Vocês vão rodar isso — com programas diferentes — na prática de hoje.
