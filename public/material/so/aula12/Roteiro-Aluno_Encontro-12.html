PASSO 1 DE 6

Montando uma estrutura de teste

Antes de manipular arquivos em lote, precisamos de arquivos para manipular — criados de forma controlada, para não haver risco.

1 mkdir -p ~/lab12/logs && cd ~/lab12 && touch relatorio{1..5}.txt sistema{1..3}.log notas.md
O que é

mkdir -p cria o diretório e os pais que faltarem. O {1..5} é expansão de chaves: o shell gera relatorio1.txt até relatorio5.txt automaticamente.

Por que importa

Já é um coringa em ação — nove arquivos criados com um comando só, em vez de nove touch separados.

$ mkdir -p ~/lab12/logs && cd ~/lab12 && touch relatorio{1..5}.txt sistema{1..3}.log notas.md $ ls logs notas.md relatorio1.txt relatorio2.txt relatorio3.txt relatorio4.txt relatorio5.txt sistema1.log sistema2.log sistema3.log

O que esperar: nove arquivos e um diretório logs vazio. Trabalhe sempre dentro de ~/lab12 nos próximos passos — assim nenhum comando de hoje toca seus arquivos pessoais.

PASSO 2 DE 6

A técnica de segurança: veja antes de agir

Este é o passo mais importante do roteiro. No shell não existe lixeira — o que você apaga, some. A defesa é sempre testar o padrão antes de usá-lo num comando destrutivo.

2 echo *.log e ls *.txt
O que é

Quem expande o coringa é o shell, antes do comando rodar. Então echo mostra exatamente a lista que qualquer outro comando receberia.

Por que importa

É a diferença entre apagar o que você quis e apagar o que você não percebeu que casava com o padrão.

$ echo *.log sistema1.log sistema2.log sistema3.log $ ls *.txt relatorio1.txt relatorio2.txt relatorio3.txt relatorio4.txt relatorio5.txt $ echo relatorio[12].txt relatorio1.txt relatorio2.txt

O que esperar: a lista expandida. Experimente também echo *, echo relatorio?.txt e echo *.{txt,md} pra ver como cada coringa se comporta.

Por que o echo mostra a lista se eu não digitei os nomes?
Porque o echo nunca viu o coringa. O shell substituiu *.log pela lista de arquivos correspondentes antes de chamar o echo — que apenas imprimiu o que recebeu. É exatamente isso que acontece com rm, cp e todos os outros. Por isso testar com echo é seguro e confiável.

PASSO 3 DE 6

Manipulando em lote

Agora sim — depois de confirmar o padrão no passo 2, use-o para valer.

3 mv *.log logs/ && ls logs/
O que é

Move todos os arquivos .log de uma vez para o subdiretório logs/. O mesmo mv também renomeia, quando o destino é um nome de arquivo.

Por que importa

É a resposta da pergunta do slide: organizar dezenas ou centenas de arquivos num comando, não num por um.

$ mv *.log logs/ && ls logs/ sistema1.log sistema2.log sistema3.log $ cp -r logs/ logs_backup/ $ ls logs logs_backup notas.md relatorio1.txt ...

O que esperar: os três .log agora dentro de logs/ e uma cópia completa em logs_backup/. Sem o -r no cp, copiar um diretório dá erro — teste e veja a mensagem.

PASSO 4 DE 6

Procurar arquivos e procurar conteúdo

Duas buscas diferentes: uma pelo nome do arquivo, outra pelo que está escrito dentro dele.

4 find ~/lab12 -name "*.log" e grep -rn "ERRO" ~/lab12
O que é

find percorre a árvore de diretórios procurando pelo nome. grep -rn procura dentro dos arquivos, mostrando arquivo e número da linha.

Por que importa

"Onde está esse arquivo?" e "onde aparece essa mensagem de erro?" são duas perguntas distintas, com ferramentas distintas.

$ echo "[ERRO] falha ao conectar" > logs/sistema1.log $ find ~/lab12 -name "*.log" /home/aluno/lab12/logs/sistema1.log /home/aluno/lab12/logs/sistema2.log /home/aluno/lab12/logs_backup/sistema1.log $ grep -rn "ERRO" ~/lab12 /home/aluno/lab12/logs/sistema1.log:1:[ERRO] falha ao conectar

O que esperar: o find lista caminhos de arquivos; o grep -rn mostra arquivo:linha:conteúdo. Repare que o find encontrou também a cópia em logs_backup/, mas o grep só achou a mensagem onde ela realmente foi escrita.

Meu grep não encontrou nada
Confirme que você rodou o echo "[ERRO] ..." > logs/sistema1.log antes — os arquivos criados com touch no passo 1 estão vazios. O grep diferencia maiúsculas de minúsculas por padrão; use grep -rni para ignorar essa diferença.
PASSO 5 DE 6

Substituir ou acrescentar: a diferença que importa

Os dois operadores de redirecionamento parecem quase iguais — e confundi-los é a causa clássica de "meu script apagou o log inteiro".

5 > versus >>
O que é

> substitui todo o conteúdo do arquivo. >> acrescenta ao final, preservando o que já existia.

Por que importa

Todo script que grava log usa >>. Usar > por engano descarta silenciosamente todo o histórico anterior.

$ echo "primeira linha" > relatorio.txt $ echo "segunda linha" >> relatorio.txt $ cat relatorio.txt primeira linha segunda linha $ echo "apaguei tudo" > relatorio.txt $ cat relatorio.txt apaguei tudo

O que esperar: as duas primeiras linhas convivendo, e depois desaparecendo quando o > é usado. Rode você mesmo e veja o conteúdo sumir — é uma lição que se aprende melhor vendo.

PASSO 6 DE 6

Os mesmos comandos, do lado de dentro

Vocês já usaram docker exec no Encontro 5. Agora dá pra usar de forma interativa — abrindo um shell dentro do container e trabalhando lá.

6 docker run -d --name shelldemo alpine sleep 600 depois docker exec -it shelldemo sh
O que é

-it significa interativo + terminal: em vez de rodar um comando e sair, você fica dentro do container, com um shell próprio.

Por que importa

É exatamente assim que se diagnostica um container quebrado em produção — entrando nele e usando os comandos básicos.

$ docker exec -it shelldemo sh / # pwd / / # ls / bin dev etc home proc root tmp usr var / # mkdir -p /teste && touch /teste/arq{1..3}.txt && ls /teste arq1.txt arq2.txt arq3.txt / # exit

O que esperar: o prompt muda para / # — você está dentro do container. Os coringas funcionam igual. Note que a árvore de arquivos é outra: você não vê seu ~/lab12 ali, porque é um sistema de arquivos isolado. Digite exit para voltar.

Por que "sh" e não "bash"?
A imagem alpine é mínima e não inclui o bash — só o sh, mais básico. É um bom lembrete de por que dominar os comandos essenciais importa: em imagens enxutas você não tem as ferramentas confortáveis à disposição, e não dá pra instalar nada no meio de um incidente.

Limpeza: ao sair, rode docker stop shelldemo && docker rm shelldemo.

Conexão com a teoria

Os passos 1–5 são os comandos básicos e de manipulação de arquivos do Laureano (p. 33–38 e 43–53). O passo 2 demonstra o papel do shell como interpretador descrito pelo Tanenbaum (p. 32–33): a expansão de coringas acontece no shell, antes de qualquer chamada de sistema — as mesmas chamadas que vocês rastrearam com strace no Encontro 3. O passo 5 retoma o redirecionamento de fluxos do Encontro 6, e o passo 6 é o gancho Docker do slide 10.
