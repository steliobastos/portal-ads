Situando o shell

O shell é um programa comum — e é isso que o torna poderoso

O shell não faz parte do núcleo do SO. Ele é apenas um programa que lê o que você digita, pede ao kernel que execute, e mostra o resultado. É por isso que existem vários shells diferentes e você pode trocar de um para outro.

Você — digita um comando
↓
Shell (bash) — interpreta, expande coringas, monta pipes
↓ chamadas de sistema (Encontro 3)
Kernel — cria processos, lê arquivos, acessa dispositivos
↓
Hardware

Reparem que o shell usa exatamente as chamadas de sistema que vocês rastrearam com strace no Encontro 3.

O multiplicador de força

Coringas: um padrão, muitos arquivos

Aqui está a resposta da pergunta do slide 2. Coringas (globbing) são expandidos pelo shell antes do comando rodar — o comando nem sabe que houve coringa; ele recebe a lista já pronta.

CoringaCasa comExemplo
*Qualquer sequência de caracteres*.log — todos os .log
?Exatamente um caracterearq?.txt — arq1.txt, arqA.txt
[...]Um caractere do conjuntoarq[123].txt
{a,b}Cada alternativa da listarel.{txt,pdf}

Como quem expande é o shell, echo *.log mostra exatamente o que qualquer comando receberia — a forma mais segura de testar um padrão.

Procurando

Encontrar arquivos e encontrar conteúdo

find

Procura arquivos pelo nome ou atributo

Percorre a árvore de diretórios inteira. Filtra por nome, tamanho, data, tipo — e pode executar ações sobre o que encontrar.

grep

Procura dentro do conteúdo

Já usado desde o Encontro 5 com pipes. Com -r percorre diretórios, com -n mostra a linha exata.

A combinação dos dois — find para localizar, grep para filtrar conteúdo — resolve a maioria das buscas do dia a dia.

Retomando o Encontro 6

Pipes e redirecionamento, agora como ferramenta de trabalho

Vocês já conhecem |, > e 2> desde o Encontro 6. O que muda hoje é o uso: não mais para observar o sistema, mas para produzir resultado.

OperadorO que faz
>Redireciona a saída para arquivo, substituindo o conteúdo
>>Redireciona acrescentando ao final — o que se usa em log
2>Redireciona só os erros (stderr, Encontro 6)
|Encana a saída de um comando na entrada do próximo

A confusão entre > e >> é a causa mais comum de "meu script apagou o log inteiro".

Por que isso importa pra quem trabalha com software

Onde o shell aparece na sua carreira

Não é opcional

Servidor não tem interface gráfica

Qualquer máquina em nuvem, container ou pipeline de CI se opera por linha de comando. Não há alternativa por mouse.

Diferencial real

É o que separa quem espera de quem resolve

Diagnosticar, automatizar e corrigir sem depender de terceiros — a competência mais visível em sustentação, DevOps e cloud.

Eixo do curso

Todo container é, por dentro, um shell esperando comandos

Vocês já usaram docker exec no Encontro 5 sem pensar muito nele. Agora dá pra ver o que estava acontecendo: aquele comando abre um shell dentro do container — e tudo que vocês aprenderem hoje funciona lá dentro também.

No host

Shell da sua VM

Ferramentas completas, sistema de arquivos inteiro, seus arquivos pessoais.

No container

Shell mínimo e isolado

Muitas imagens (como alpine) trazem só o essencial — e é justamente aí que dominar os comandos básicos faz diferença.

Diagnosticar um container quebrado é, quase sempre, entrar nele com docker exec -it ... sh e usar exatamente os comandos de hoje.
